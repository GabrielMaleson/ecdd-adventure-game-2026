NOTE (not a task — just documenting a known quirk):
    Two-crates "only one moves per gesture" arbitration: the losing crate is locked
    until the player RELEASES the movement input. There is one theoretical way to make
    the loser move without releasing: keep the movement input held continuously the
    whole time (never let go) while manoeuvring onto the other crate. In practice
    players release/re-press constantly, so this is a non-issue. Decided NOT to add a
    distance-based unlock (moved N units -> unlock) — it needs a magic threshold and
    risks reopening the "wrong crate moves" bugs. Left as-is on purpose.

NEW MECHANIC I want to build — what Claude understood (TileCycle)
------------------------------------------------------------------------
The "cycling bushes / moving gap" puzzle, driven by the statue:
  - A RING of cells. Bushes CYCLE through them, one step each time the statue is used
    (E). With FEWER bushes than cells, one cell is always empty — a GAP that
    circulates around the ring, opening a path where a bush just vacated.
  - TOP crate: 2 bushes / 3 cells (the 3 cells directly adjacent to the top crate:
    left, up, right). 1 gap circulates.
  - BOTTOM crate: 1 bush / 3 cells. 2 gaps.
  - This is DIFFERENT from the statue's rigid 90-degree rotation (ObstacleGroup):
    that turns a whole shape; this shifts occupancy around a fixed ring.

  TileCycle.cs is written. Setup per cycle:
    1. Parent GameObject + TileCycle component.
    2. Children, in cycle order: the bushes (each with GridObstacle) + a Create-Empty
       marker on each GAP cell (top: 1 empty; bottom: 2 empties). Snap all.
    3. Add the TileCycle to the statue's StatueSwitch -> Cycles list (new field,
       alongside Groups). Statue moves groups + cycles together, all-or-nothing.
    4. Direction = the Reverse checkbox on TileCycle. Flip it if the gap goes the
       wrong way. (No coordinates needed — the component reads the children.)
